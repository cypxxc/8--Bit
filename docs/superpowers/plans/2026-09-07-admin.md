# 8bit owner backend implementation plan

Scope approved in conversation: owner login, dashboard, website and walk-in service requests, job details and status, editable services/prices, LINE notification history. Chat remains in LINE OA Manager.

1. Create Supabase tables with RLS and no direct public access to customers, staff membership, notifications, or rate limits. Public service listing goes through a server endpoint that exposes only enabled catalog records.
2. Use Supabase Auth with server-managed HttpOnly cookies and check owner membership on every admin endpoint. Provision only the user-specified owner. Provide a one-time password setup screen, without emailing or revealing a password.
3. Save validated website requests before LINE delivery; generate server IDs, require idempotency keys, rate-limit intake, persist one notification record per request, and use LINE retry keys when retrying uncertain outcomes.
4. Build an admin workspace for search, status filters, pagination, walk-in intake, details, internal notes, equipment, quoted price, and catalog management. Require explicit owner action for retries. Store optimistic versions to reject stale edits.
5. Feed storefront cards, pricing, and intake options from the managed catalog. Do not show simulated success when persistence fails.
6. Verify input validation, anonymous denial, non-owner denial, persistence, deduplication, catalog edits, status updates, notification behavior without sending unsolicited messages, desktop/mobile UI, lint, types, and production build.

Implementation files: `lib/backend/*` server boundaries, `app/api/admin/*` protected endpoints, `app/api/services` public catalog, `app/api/ticket` intake, `components/admin/*` operator interface, `app/admin/*` entry points, `supabase/migrations/*` reproducible schema, `tests/*` focused verification.

No deployment or inbound LINE chat sync is included. Production environment variables must be configured separately from the local `.env.local`.
